# 4. Интеграция с МИС и «Витакором»

**Статус: нет доступа к реальному API, тестовой среде и документации по конкретному контуру.** Не считать предложенные поля или события существующими эндпоинтами «Витакора». В республиканской ГИС есть функции электронной очереди; необходимо выяснить, доступны ли они в целевом учреждении и почему не применяются. Сначала проверить возможность штатной настройки.

## Вопросы к поставщику МИС

1. Какие модули очереди уже существуют, где они развернуты, есть ли подтверждение прибытия и интерфейс вызова? Какие проблемы остаются?
2. Какие интерфейсы доступны внешнему модулю: REST, HL7/FHIR, локальный сервис, события? Есть ли sandbox, спецификация, порядок согласования и стоимость подключения?
3. Можно ли получать расписание, изменения записи, перенос кабинета, статус приёма; где источник истины для каждого статуса?
4. Допускается ли передача статусов check-in и вызова обратно, запуск штатной кнопки из МИС, а не отдельная ручная панель?
5. Кто отвечает за развёртывание, защиту информации, доступы и поддержку? Кто согласует пилот?

## Предлагаемый внутренний контракт (не API вендора)

- `AppointmentRef`: внешний непрозрачный ID, facility_id, room_id, scheduled_start/end, state, version. Минимум данных, без ФИО на табло.
- `AppointmentChanged`: event_id, event_type, occurred_at, appointment_ref, version. Уникальный ID доставки и проверка версии.
- Адаптер: `list_appointments`, `get_appointment`, `record_arrival`, `record_queue_event` — только после подтверждения возможностей и прав.
- Синхронизация: первоначальный snapshot, затем события или разрешённый polling; идемпотентность, повторная доставка, журнал конфликтов, периодическая сверка.

МИС по умолчанию остаётся источником истины для записи, расписания и медицинского визита; модуль очереди — для своих событий вызова/ожидания. Матрицу владения каждым статусом согласовать с вендором. Не изменять записи в БД МИС напрямую и не скрейпить интерфейс с персональными данными.

## Без интеграции

Демо на синтетических кодах. В v0.2 `POST /api/staff/demo-appointments` принимает `booking_code` (DEMO-…), `room_id` и `scheduled_at` с часовым поясом; повтор точно такого же импорта не создаёт новую запись. Это локальный тестовый seam, а не интеграция с вендором. Обновление/отмена записи внешней системой и разрешение конфликтов ещё не реализованы. Для исследования процесса возможен согласованный теневой пилот без данных реальных пациентов и без влияния на расписание. Если API закрыт, рассмотреть поставку экранов под штатный модуль, партнёрство с вендором или остановку идеи.
