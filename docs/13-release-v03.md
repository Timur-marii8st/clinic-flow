# v0.3 — серверное ядро (кандидат для демонстрации)

## Изменения

- Чистые правила сортировки и переходов в app/domain/queue_policy.py; общий сервис команд в app/services/queue.py; SQLiteStore и PostgresStore в app/repositories. Старый импорт app.queue.Queue и API сохранены.
- PostgreSQL 17, SQLAlchemy Core 2, psycopg 3 и первая миграция Alembic. SQLite v1/v2 обновляется до схемы v3 без намеренного удаления данных. В обоих вариантах сохраняются талоны, этапы, история и уникальность активного вызова.
- POST /api/staff/rooms — создание/изменение названия кабинета, без удаления; форма на странице врача для демо. Это не production RBAC. Перезагрузите терминал для нового списка кабинетов.
- Заголовок Idempotency-Key (16–100 символов) для call-next, action и transfer. Успешный ответ записывается вместе с изменением состояния в одной транзакции. Повтор с тем же payload возвращает первоначальный ответ, а не новый вызов; использование ключа для другого payload возвращает 409. Неуспешная команда откатывается и не занимает ключ. UI повторяет транспортный сбой один раз с прежним ключом. После неясного результата сначала обновить состояние, не начинать новый вызов вслепую.
- Команды без заголовка всё ещё поддерживаются для v0.2-клиентов. Check-in и выдача walk-in сохраняют существующую семантику; полная единообразная идемпотентность всех записей — следующий этап.
- SQLite использует BEGIN IMMEDIATE; PostgreSQL — advisory xact lock на схему и READ COMMITTED для записей, REPEATABLE READ для чтения. Это простой, консервативный вариант для одного участка: все изменения сериализуются. Не обходить этот lock прямой записью в БД. Блокировки отдельных кабинетов и реальная многоклиентская производительность ещё не проверены.
- Тimestamps пока сохраняют канонический UTC ISO формат старого API. Переход на native timestamptz, facility scoping, ORM-модель и индивидуальная IAM/RBAC отложены; SQLAlchemy используется как Core, не полноценный ORM.
- SSE остаётся локальным сигналом процесса + 10-секундный heartbeat/snapshot. Один Uvicorn worker для мгновенного обновления. Общий transport (LISTEN/NOTIFY или revision poller) — отдельная следующая задача, не часть этого релиза.

## Запуск локального стенда

SQLite как прежде: docker compose up --build -d.

Для PostgreSQL (отдельный Compose-профиль, не поднимать одновременно на том же порту):

    # укажите собственный локальный пароль через окружение / .env
    docker compose -f compose.postgres.yaml up --build -d

Порт приложения только 127.0.0.1:8000; БД не публикуется. При запуске контейнер выполняет alembic upgrade head. Не раскрывайте DB URL и пароли в Git. Без Docker: установить requirements.txt, настроить CLINIC_DATABASE_URL (postgresql+psycopg) в окружении, выполнить python -m alembic upgrade head и запустить один worker Uvicorn.

## Перенос старого стенда

Только синтетические данные! Остановить исходное приложение, сохранить копию SQLite (при WAL использовать штатный backup SQLite или корректно остановленный файл). Создать отдельную чистую PostgreSQL БД. Указать CLINIC_DATABASE_URL, выполнить alembic upgrade head, но пока не запускать приложение (оно заполняет demo seed).

    python -m scripts.import_sqlite /path/to/backup.sqlite3 --confirm-demo

Утилита проверяет integrity и версию 2/3, читает источник без записи, переносит строки и ID, этапы и события (для v3 — command_keys), сверяет количество, восстанавливает PostgreSQL sequence и отклоняет непустую цель. Табличные данные переносятся транзакционно; PostgreSQL sequences не транзакционны, при ошибке возможны безопасные пропуски ID в ещё пустой БД. Сверить сценарии в новой БД, исходник сохранить отдельно. Для отката остановить новую версию и использовать сохранённую старую БД/версию кода; downgrade PostgreSQL удаляет таблицы и не должен применяться к рабочим данным.

## Проверки

CI: pytest с временными PostgreSQL-схемами и SQLite, Playwright, smoke SSE, проверка JS. TEST_POSTGRES_URL должен указывать на выделенную тестовую БД, никогда на рабочую. Без этого значения PostgreSQL-тесты пропускаются. Состояние проверок смотреть в GitHub Actions для соответствующего commit SHA. Нагрузочный тест, Docker на реальном устройстве, failover и интеграция с МИС пока не выполнены.

Ограничение: v0.3 — только синтетический стенд. Не использовать для реального приёма; авторизация, TLS, политика доступа, регламент и интеграция требуют дальнейшего внедрения.
