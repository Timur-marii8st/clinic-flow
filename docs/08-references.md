# 8. Open-source исследование и архитектурные решения

Срез на момент подготовки v0.2. Изучены публичные README, документация и описание репозиториев. Это сравнительный дизайн-анализ, а не полноценный аудит исходников, зависимостей или независимое тестирование конкурентов. Код Clinic Flow написан самостоятельно; сторонние проекты не вендорились. Проверка лицензии нужна перед любым прямым заимствованием кода.

## Что делать быстрее, а что отложить

- Не форкать целую МИС: API поставщика и локальная оркестрация — главный продуктовый риск. Демо остаётся FastAPI + SQLite, браузер без npm-сборки, один сервер.
- SSE передаёт лишь сигнал об изменении; запрос snapshot всегда читает актуальное состояние. Не нужен broker на первом стенде. Один worker для мгновенного уведомления. Если нагрузочный тест выявит предел, PostgreSQL и общий механизм уведомления/outbox — следующий шаг.
- SQLite WAL и короткие write-транзакции; ограничения уникальности активного вызова и открытого этапа. Конкурентный вызов и повторы выдачи покрыты тестами.
- Прогноз ожидания: считать вход→начало, начало→окончание, отдельно по кабинету и типу визита. Для будущего ETA использовать медиану/квантили и оценить ошибку на временном holdout; не обещать пациенту точное время. ML только если baseline недостаточен. Нынешняя аналитика — по последним 100 закрытым этапам кабинета; это не модель предсказания.
- Порядок записи, 30-минутное aging и допустимые переводы — гипотезы, не клинический регламент. Не автоматизировать медицинскую срочность. Не отменять запись до приёма автоматически.
- Не хранить ФИО на табло; не добавлять камеры/микрофоны. Проверить доступность озвучки на конкретном Orange Pi и возможность полностью локального синтеза. Для пилота предпочтителен локальный TTS с заранее проверенными голосами.

## Региональный контекст

- [Документация Vitacore](https://wiki.vitacore.ru/pages/viewpage.action?pageId=438076051): исходная ссылка из обсуждения. Проверить актуальный штатный модуль очереди у поставщика, не предполагать доступность API.
- [Инфоматика: пример внедрения](https://infomatika.ru/projects/system-electronic-queue-information-and-payment-terminals/respublikanskaya-klinicheskaya-infektsionnaya-bolnitsa-im-prof-a-f-agafonova-g-kazan/): пример локального поставщика оборудования, ссылка из предыдущего обсуждения.

Следующая сравнительная проверка — развёртывание QMS и OpenMRS на синтетическом сценарии трёх кабинетов с учётом ресурсов, количества действий врача, скорости вызова, доступности, интеграции и лицензирования. Текущая работа не доказывает, что Clinic Flow быстрее конкурентов.
