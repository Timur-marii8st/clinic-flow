# 1. Продукт и требования

## Проблема и позиционирование

Электронная запись не всегда делает движение пациента по поликлинике прозрачным: люди спрашивают, кто последний, ждут у неверной двери, врачу приходится выходить из кабинета, неявки создают простои. Причины неоднородны: перегруженное расписание, длительность приёмов, сочетание записанных и пришедших без записи, неактивированные функции МИС. Это гипотезы для проверки, не доказанный спрос.

**Продукт:** локальный модуль управления пациентскими потоками, интегрированный с действующей МИС, а не новая МИС. Базовые электронные очереди уже существуют; преимущество должно выражаться в меньшем времени ожидания, меньшем числе ручных действий, эффективной маршрутизации или более простом внедрении.

## Пользователи

- Пациент: подтверждает прибытие, получает понятный маршрут, видит и слышит номер вызова; не обязан пользоваться смартфоном.
- Врач: вызывает следующего пациента из рабочего интерфейса, отмечает начало/окончание без двойного ввода.
- Регистратор/медсестра: помогает пациентам без записи, обрабатывает исключения, корректирует маршрут с основанием.
- Руководитель: видит время ожидания, загрузку, неявки, простои; не получает ложных KPI из неполных данных.
- ИТ-служба: контролирует интеграцию, сеть, состояние устройств, доступ и журнал.

## Основные сценарии

| Сценарий | Целевое поведение | Статус |
|---|---|---|
| Запись заранее | МИС передаёт назначение и кабинет, пациент отмечает прибытие | Тестовый код в демо; реальной интеграции нет |
| Приход без записи | Сотрудник направляет по правилам учреждения, неотложная помощь вне общей очереди | Свободная выдача синтетических талонов только в демо |
| Вызов | Номер талона и кабинет на экране; голос дублирует текст | Экран и опциональная озвучка в браузере реализованы в v0.2 |
| Неявка | Повторный вызов, ручная отметка после установленного интервала; восстановление по правилам | Ручная отметка после вызова и восстановление есть |
| Опоздание | Не отменять до начала слота; регистратор определяет доступное окно | Проектирование с клиникой |
| Перенос кабинета | Согласованное обновление МИС, маршрут и экран обновляются | Ручной перенос в демо; синхронизация с МИС в backlog |
| Несколько процедур | Перестановка только допустимых этапов, с учётом ресурсов и клинических ограничений | История этапов есть; автоматическая маршрутизация в backlog |
| Потеря сети | Экран прекращает показывать устаревшие вызовы; сотрудник ведёт приём штатным способом | Демо скрывает устаревшие данные; регламент нужен |

## MVP и антицели

MVP пилота: один участок/три кабинета, подтверждение прибытия, управляемый вызов, табло, регистрация событий, ограниченный адаптер МИС, роли и безопасная сеть. Для демо выбран ещё более узкий срез без реальной интеграции.

Не обещаем сокращение очереди при дефиците врачей, не запрещаем приём без записи, не отменяем запись автоматически за 15 минут до визита, не показываем ФИО/диагнозы на экране. Нет диагностики, биометрии, камер и микрофонов. ML не нужен для первого этапа. В дальнейшем прогноз времени ожидания проверяется против простого статистического baseline.
